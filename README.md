# fable-skills

Fable 5 の高品質な作業を支えている「仕組み」を洗い出し、Opus / Sonnet など既存の LLM モデルでも再現できるように Skill 化したコレクションです。

## 設計思想: Fable の品質はどこから来るのか

Fable クラスのモデルが高品質に見える理由を分解すると、大きく2つに分かれます。

| 要素 | 内容 | Skill で移植できるか |
|---|---|---|
| **作業規律(プロセス)** | 着手前のスコープ確定、並列探索、敵対的検証、実挙動での確認、結論ファーストの報告、自律的な完遂 | ◎ 移植可能(このリポジトリの主対象) |
| **生の推論力** | 一発で深い仮説に到達する力、長いタスクでの一貫性、暗黙の文脈の補完 | △ 部分的(検証ループの回数を増やすことで補償する) |

体感される品質差の多くは前者(プロセス)に由来します。つまり **「何を考えるか」より「どういう順序・規律で作業するか」を強制すれば、Opus でも Fable に近い成果物が出せます**。後者の差は、検証の回数・角度を増やす(1回で正解する代わりに、生成→反証→修正を回す)ことで大部分を埋められます。

## 構成

### 2層アーキテクチャ

1. **常時適用レイヤー(`templates/CLAUDE-fable-core.md`)**
   Skill は「必要なときにロードされる」プル型の仕組みなので、常に効かせたい基本規律は CLAUDE.md に書く必要があります。このテンプレートを各プロジェクトの `CLAUDE.md` に追記(または `~/.claude/CLAUDE.md` に配置)してください。

2. **Skill レイヤー(`skills/`)**
   場面ごとの詳細な手順書。タスクの種類に応じて自動ロード、または `/fable-mode` で明示的に起動します。

### Skill 一覧

| Skill | 役割 | Fable の対応メカニズム |
|---|---|---|
| `fable-mode` | 全 Skill を束ねるオーケストレーター。実質的な「Fable モード」の入口 | タスク全体の進め方の型 |
| `scope-and-plan` | 着手前のスコープ確定・成功条件の定義・計画 | 曖昧な依頼を作業可能な形に変換してから動く |
| `parallel-explore` | 複数角度からの並列コード探索 | ファンアウト探索と結論のみの統合 |
| `deep-investigate` | 調査・分析タスクの多モード探索と三角測量 | 構造・内容・時系列・エンティティの複数角度探索 |
| `adversarial-verify` | 自分の結論を「反証する」検証 | 敵対的検証・複数レンズでの判定 |
| `evidence-verify` | 実際にコードを動かして挙動で確認 | テスト通過≠動作、エンドツーエンド検証 |
| `root-cause-debug` | 再現→仮説→判別→根本原因の修正 | 症状ではなく機構を直す debugging 規律 |
| `autonomous-drive` | エラーや不足情報で止まらず完遂する | 自律推進ループ |
| `context-discipline` | 必要な部分だけ読む・確定事実を再導出しない | コンテキスト規律 |
| `quality-pass` | 実装後の簡素化・再利用・コメント規律のセルフレビュー | 出荷前の品質パス |
| `report-tldr` | 結論ファースト・再読不要な報告の書き方 | 報告構造の規律 |

## 前提条件

- [Claude Code](https://code.claude.com/docs) がインストール済みであること(CLI / デスクトップアプリ / IDE拡張のいずれでも可)
- 導入したいプロジェクトのフォルダがあること(なくても「方法B: ユーザー全体」なら導入可能)

Skill の知識は不要です。以下の手順をコピペすれば動きます。

## インストール

> **重要**: 手順は「① Skill のコピー」と「② CLAUDE.md への追記」の**2つでワンセット**です。
> Skill は「関連するタスクのときだけ読み込まれる」プル型の仕組みなので、①だけでは普段の細かい作業に規律が効きません。常に効かせたい基本規律(テスト通過≠動作、結論ファースト報告など)は、毎回必ず読み込まれる CLAUDE.md に書く必要があります(②)。

まず、このリポジトリを手元に取得します:

```bash
git clone https://github.com/ohigashi-tky/fable-skills.git
cd fable-skills
```

### 方法A: プロジェクト単位で導入(まず試すならこれ)

特定のプロジェクトだけに効かせます。`.claude/` フォルダごと git にコミットすれば、**チームメンバー全員の Claude Code にも同じ規律が効きます**。

```bash
# ① Skill をプロジェクトにコピー
mkdir -p /path/to/your-project/.claude/skills
cp -r skills/* /path/to/your-project/.claude/skills/

# ② 常時適用レイヤーを CLAUDE.md に追記(CLAUDE.md がなければ新規作成されます)
cat templates/CLAUDE-fable-core.md >> /path/to/your-project/CLAUDE.md
```

`/path/to/your-project` は導入したいプロジェクトのパスに置き換えてください。

### 方法B: ユーザー全体に導入(全プロジェクトに一括適用)

手元の全プロジェクトに効かせたい場合はこちら。プロジェクトごとのコピーは不要になります。

```bash
# ① Skill をユーザーの skills フォルダにコピー
mkdir -p ~/.claude/skills
cp -r skills/* ~/.claude/skills/

# ② 常時適用レイヤーをユーザーの CLAUDE.md に追記
cat templates/CLAUDE-fable-core.md >> ~/.claude/CLAUDE.md
```

方法Aと方法Bは併用できます(両方にある場合はプロジェクト側が優先的に使われます)。まず方法Aで1プロジェクト試し、良ければ方法Bに昇格させるのがおすすめです。

### 方法C: プラグインとして導入(上級者向け・任意)

このリポジトリは Claude Code プラグイン構造(`.claude-plugin/plugin.json`)を持っているため、marketplace に登録して `/plugin` コマンドからインストールすることもできます。通常は方法A/Bで十分です。

### 導入できたかの確認

導入先のプロジェクトで **新しいセッションを開始**し(既存セッションには反映されません)、次のように聞いてください:

```
このプロジェクトで使えるスキルを教えて
```

`fable-mode` や `adversarial-verify` などが一覧に出れば導入成功です。出ない場合は「うまく動かないとき」を見てください。

## 使い方

導入後は基本的に**何もしなくても効きます**。使い方は3段階です。

### 1. 普段のタスク: そのまま依頼するだけ

CLAUDE.md の常時適用レイヤーが基本規律(着手前のスコープ確認、実挙動での検証、結論ファーストの報告など)を効かせます。タスクの内容に応じて、関連する Skill(バグ調査なら `root-cause-debug`、調査依頼なら `deep-investigate` など)が自動で読み込まれます。

### 2. 重要なタスク: `/fable-mode` を付けて依頼する

品質を最優先したいタスクでは、依頼の先頭に `/fable-mode` を付けます:

```
/fable-mode 決済処理のリトライ機構を実装して
```

スコープ確定 → 並列探索 → 実装 → 実挙動検証 → 反証検証 → 品質パス → 報告、の全パイプラインが明示的に走ります。時間とトークンは通常より多く消費します。

### 3. 特定の規律だけ効かせたいとき: Skill 名で個別起動

```
/adversarial-verify さっきの調査結果を検証して
/root-cause-debug このテストが落ちる原因を調べて
/report-tldr ここまでの結果をまとめて
```

### 効果が出ているかの見分け方

導入前後で、次の変化が見えれば効いています:

- 実装タスクで「テストが通った」ではなく「実際に◯◯を実行して△△が出ることを確認した」と報告してくる
- 報告の第一文が結果になっており、「確認済み / 未確認」が分けて書かれている
- 調査結果に file:line の根拠が付き、断定と推測が書き分けられている
- エラーが出ても質問で止まらず、自分でリトライ・回避して進む

## うまく動かないとき

| 症状 | 原因と対処 |
|---|---|
| スキル一覧に出てこない | 配置ミスの可能性。`ls .claude/skills/fable-mode/SKILL.md` でファイルの存在を確認。`skills/fable-mode` の**中身のフォルダごと**コピーされている必要があります(`.claude/skills/skills/...` になっていたら1階層ずれ) |
| 一覧には出るが自動で使われない | Skill の自動起動は依頼文とのマッチングに依存します。確実に効かせたい場面では `/fable-mode` など明示起動を使ってください |
| 普段の作業で規律が効いていない | ②の CLAUDE.md 追記を忘れている可能性が高いです。`grep "Fable Core" CLAUDE.md` で確認 |
| 導入したのに反映されない | 既存セッションには反映されません。新しいセッションを開始してください |
| 動作が重い・トークン消費が増えた | 仕様です(検証ループの分)。普段は自動適用に任せ、`/fable-mode` は重要タスクに絞ってください |

## Opus で Fable 並みの品質は出るのか(正直な評価)

**出せる領域(このリポジトリでほぼ埋まる):**
- 調査・分析の網羅性と正確さ(並列探索+敵対的検証で担保)
- 実装タスクの「動くものを出す」率(evidence-verify の強制で担保)
- 報告の読みやすさ・信頼性(report-tldr で担保)
- タスクを途中で投げ出さない完遂率(autonomous-drive で担保)

**差が残る領域と緩和策:**
- **一発の推論の深さ**: 難問では Opus は最初の仮説が浅いことがある → adversarial-verify のループ回数を増やす(生成→反証→修正を2〜3周)ことで到達点を近づける。時間とトークンは余分にかかる。
- **超長期タスクの一貫性**: コンテキストが伸びると規律が薄れる → context-discipline の「状態ノート」運用と、フェーズごとのサブエージェント分割で緩和。
- **暗黙の意図の察知**: 指示の行間を読む力 → scope-and-plan で最初に明示化を強制することで、察する必要自体を減らす。

**推奨設定:** Opus を使う場合は extended thinking を有効にし、検証系 Skill(adversarial-verify / root-cause-debug)では思考予算を多めに取ってください。コストより品質が優先の場面では、同じ検証を独立に2回走らせて突き合わせるのが最も効きます。
