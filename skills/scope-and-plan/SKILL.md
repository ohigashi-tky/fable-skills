# Scope and Plan — 着手前のスコープ確定

曖昧な依頼を「作業可能で、完了判定ができる」形に変換してから動く。Fable の品質の相当部分は、**間違ったものを高品質に作らない**ことから来ている。

## 手順

### 1. 言い換えテスト

タスクを自分の言葉で1〜2文に言い換える。以下を必ず含める:

- **完了条件**: 何が満たされたら完了か(「〜が動く」「〜が分かる」レベルで具体的に)
- **成果物の形**: コード変更 / 分析レポート / 回答 / 設計案 のどれか

言い換えができない = 理解できていない。先に進まず不明点を特定する。

### 2. 依頼の型を判定する

| ユーザーの発話 | 成果物 | やってはいけないこと |
|---|---|---|
| 「〜がおかしい」「〜ってどうなってる?」 | 分析・回答 | 頼まれていない修正の適用 |
| 「〜を直して」「〜を作って」 | コード変更 | 分析だけして止まる |
| 「〜したい。どうすればいい?」 | 提案(+承認後に実装) | 承認前の大規模変更 |

### 3. 不明点の処理

不明点を列挙し、それぞれを3分類する:

1. **調べれば分かる** → 自分で調べる。ユーザーに聞かない。
2. **合理的なデフォルトがある** → デフォルトを選び、報告に明記して進む。
3. **ユーザーにしか決められない**(要件そのもの、トレードオフの優先度、破壊的操作の可否)→ 今まとめて聞く。作業途中で1個ずつ聞かない。

### 4. 非目標を書く

「今回やらないこと」を最低1つ明示する。例: 「リファクタは対象外」「他モジュールへの波及は今回見ない」。スコープ膨張と、逆に勝手な縮小の両方を防ぐ。

### 5. 計画は検証可能な増分で

- 各ステップが「終わったことを確認できる」単位になっているか確認する。
- 「実装する」ではなく「Xを変更し、Yを実行してZが出ることを確認する」と書く。
- 最初に着手すべきは**最も不確実性が高い部分**(そこが無理なら計画全体が変わるため)。

## アンチパターン

- 理解が曖昧なまま「とりあえず探索」を始めて、30分後に的外れな方向にいる
- 選択肢を並べてユーザーに丸投げする(推奨を1つ決めて提示する)
- 計画を書いたことに満足してターンを終える(計画は成果物ではない。すぐ実行に移る)
- 質問タスクなのにコードを書き換えてしまう
