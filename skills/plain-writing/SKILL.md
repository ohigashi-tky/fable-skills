# Plain Writing — 冗長でない自然な文書

読者は文章を読みたいのではなく、用を済ませたい。1回読んで用が済むのが良い文章。AIが書く文章は「網羅しようとして水増しする」「同じことを何度も言う」「意義を語る」で長くなる。これを禁止する。

## 書く前に決めること

「読者は誰で、読んだ後に何をするか」を1行で決める。その行動に不要な情報は書かない。

## 禁止パターン

| パターン | 例 | 代わりに |
|---|---|---|
| 前置き | 「本ドキュメントでは〜について説明します」 | いきなり本題から始める |
| 自明な意義の説明 | 「テストは品質にとって重要です」 | 削除 |
| 同じ内容の繰り返し | 概要で言い、本文で言い、まとめでまた言う | 1回だけ書く |
| 誇張形容詞 | 徹底的に・強力な・高品質な・柔軟な・シームレスに | 事実か数字に置き換える。できなければ削除 |
| 冗長な言い回し | 〜することができます / 〜する必要があります | 〜できます / 〜してください |
| 網羅風の水増し | 使わない選択肢や起きないケースの列挙 | 読者の行動に関係するものだけ |
| 構造の過剰 | 3行で済む内容に見出し3つと表と箇条書き | 段落で書く。表は比較が本当に必要なときだけ |
| 締めの常套句 | 「以上を踏まえ、適切に運用することが望まれます」 | 削除(何も言っていない) |

## 書いた後にやること

各文に「この文を消したら読者が困るか?」と問い、困らない文を消す。初稿が半分になるのは普通。

読み返して「だからなに?」と感じる文があれば、それが冗長さの正体。消すか、読者の行動につながる情報に書き換える。

## 文書タイプ別の型

- **README**: これは何か(2〜3文)→ 導入手順 → 使い方。設計思想の長話は別ファイルへ
- **設計書・仕様書**: 決めたことと理由を書く。選ばなかった案は1行ずつで十分。実装の逐語説明はしない(コードを読めば分かる)
- **コードコメント**: コードで表現できない制約のみ。処理の説明・変更理由・履歴は書かない
- **コミットメッセージ・PR説明**: 何が変わるか1行 → レビュアーが知るべき背景。作業の時系列日誌にしない
