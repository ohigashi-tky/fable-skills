# Fable Mode — 高品質タスク実行パイプライン

実質的なタスク(実装・調査・分析・デバッグ)を Fable 品質で完遂するためのオーケストレーター。各フェーズの詳細は対応する Skill を参照するが、この文書だけでも全体は回せる。

## パイプライン

### Phase 0: 分類とキャリブレーション

まずタスクを分類し、かけるべき重さを決める。**全フェーズを常に回すのではない。**

| タスク | 実行するフェーズ |
|---|---|
| 1ファイルの明白な小修正 | 3 → 4(evidence-verify のみ)→ 6 |
| 通常の実装タスク | 1 → 2 → 3 → 4 → 5 → 6 |
| 調査・分析・質問 | 1 → 2(deep-investigate)→ 4(adversarial-verify)→ 6 |
| バグ修正 | 1 → root-cause-debug → 4 → 5 → 6 |
| 「徹底的に」と言われたタスク | 全フェーズ + 検証を独立2回 |

### Phase 1: スコープ確定(scope-and-plan)

1. タスクを自分の言葉で1〜2文に言い換える(完了条件を含める)。
2. 「質問」か「変更依頼」かを判定する。質問なら成果物は分析であり、修正しない。
3. 非目標(やらないこと)を1つ以上明示する。スコープ膨張の防波堤になる。
4. ユーザーにしか決められない決定があれば今聞く。なければデフォルトを選んで進む。

### Phase 2: 探索(parallel-explore / deep-investigate)

- 影響範囲のファイル・シンボル・呼び出し元を**複数角度**(名前・内容・構造・git履歴)から特定する。
- サブエージェント(Task/Agent ツール)が使えるなら独立した探索を並列に投げ、結論だけ受け取る。
- 探索の成果は「file:line 付きの事実リスト」としてまとめてから次に進む。

### Phase 3: 実装

- 大きな変更は検証可能な小さい増分に割る。1増分ごとに動作確認できる状態を保つ。
- 周囲のコードの流儀に合わせる。コメントは制約の記述のみ。
- 途中でエラーに当たったら autonomous-drive の規律(リトライ・代替・自力調査)で自分で抜ける。

### Phase 4: 検証(最重要 — ここが品質差の源泉)

**4a. evidence-verify(実挙動):**
- テスト・型チェックだけで済ませない。変更したフローを実際に動かし、出力・ログ・画面を観察する。

**4b. adversarial-verify(反証):**
- 自分の結論・修正それぞれに対し「これが間違っているとしたら、どういう入力・状態で壊れるか」を具体的に構成する。
- 構成した失敗シナリオを実際に試すか、コードを読み直して成立しないことを確認する。
- 反証できてしまったら Phase 3 に戻る。**このループを最低1周、「徹底的に」案件では2〜3周回す。**
- 判定は CONFIRMED(実証した)/ PLAUSIBLE(実証していない)を区別して持つ。PLAUSIBLE を CONFIRMED として報告しない。

### Phase 5: 品質パス(quality-pass)

- diff をハンクごとに読み、簡素化・重複・不要コメント・デッドコードを除去する。
- リンター・フォーマッターがあれば実行する。

### Phase 6: 報告(report-tldr)

- 最初の1文 = 結果。以降に根拠と詳細。
- 確認済み/未確認を区別し、失敗やスキップは正直に書く。
- 最終メッセージだけで全体が伝わること(途中のメッセージは読まれていない前提)。

## アンチパターン(Fable がやらないこと)

- 探索を1回の grep で済ませて「見つかりませんでした」と報告する
- テストが通った時点で「完了しました」と言う
- 検証フェーズを「時間がないので」省略する(省略するのは Phase 1-2 側であって 4 ではない)
- 長いタスクの後半で規律が薄れ、最後の変更だけ未検証で出す
- ユーザーへの質問でターンを終えて作業をブロックする(デフォルトで進めるべき場面で)
