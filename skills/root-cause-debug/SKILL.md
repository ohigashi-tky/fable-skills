# Root Cause Debug — 根本原因デバッグ

症状に対して最初に思いついた修正を当てるのではなく、**機構(なぜそうなるか)を特定してから直す**。Fable のデバッグが速いのは勘が良いからではなく、仮説を証拠で絞る手順が速いから。

## 手順

### 1. 再現する(最初に、必ず)

- 修正を考える前に症状を自分の環境で再現する。再現できない問題は直せたかどうか判定できない。
- 再現手順を最小化する(不要な手順・データを削る)。最小再現は仮説の判別器になる。
- 再現できない場合: 環境差分(バージョン・設定・データ)を列挙して1つずつ潰す。それでも無理なら「再現不能」という事実と試した条件を報告する。勘で修正しない。

### 2. エラーを実際に読む

- スタックトレース・ログは**全文**読む。最後の1行だけで判断しない。最初に発生したエラーと、それに引きずられた二次エラーを区別する。
- エラーメッセージでコードベースを Grep し、発生箇所を特定する。

### 3. 競合する仮説を立てる

- 仮説を**最低2つ**立てる(1つしかない仮説は検証ではなく確認になりがち)。
- 各仮説について「この仮説が正しいなら X が観察されるはず / 間違っているなら Y のはず」という**判別可能な予測**を書く。

### 4. 証拠で絞る

- ログ追加・デバッガ・最小スクリプトで、仮説を判別する観察を行う。
- `git log` / `git bisect` は強力な判別器: いつから壊れたかが分かれば原因コミットが機構を教えてくれる。
- 予測と観察が食い違ったら仮説を捨てる。**観察に合わせて仮説を歪めない。**

### 5. 機構を1文で言えるまで掘る

「◯◯という条件のとき、△△が □□ になるため、××が起きる」と書けたら根本原因に到達している。書けないうちは修正に進まない。

### 6. 修正と検証

- 症状ではなく機構を直す(null チェック追加で黙らせる前に、なぜ null が来るのかを問う)。
- 修正前に再現 → 修正後に非再現を**両方**確認する(evidence-verify)。
- **同型のバグを探す**: 同じ機構が他の場所にもないか、原因パターンで Grep する。Fable はここで「ついでに3箇所同じバグがあります」を出す。

## アンチパターン

- 再現せずにコードを眺めて「たぶんここ」で修正を当てる
- エラーメッセージをよく読まずに検索・修正を始める
- 1つ目の仮説を支持する証拠だけ集める(確証バイアス)
- 症状が消えたら機構を理解しないまま完了にする(偶然消えただけの可能性)
- try/catch や null チェックで症状を隠して「修正」と称する
