# Evidence Verify — 実挙動による検証

**テストが通った ≠ 動く。型が合った ≠ 正しい。** Fable は「should work」を報告に書かない。動かして観察した事実だけを「動く」と報告する。

## 手順

### 1. 検証対象のフローを特定する

変更が影響する**ユーザーから見える挙動**は何か。「関数 X を変えた」ではなく「コマンド Y を打つと Z が出る」のレベルで特定する。

### 2. エンドツーエンドで動かす

変更したコードが実際に通る経路で実行する:

- CLI なら実際にコマンドを打つ
- API ならサーバを起動して実リクエストを送る
- UI なら起動して操作する(スクリーンショット・DOM で確認)
- ライブラリなら呼び出しスクリプトを書いて実行する
- バッチ・スクリプトなら実データに近い入力で流す

**単体テストの追加・実行は「補助」であって、この代替にならない。** テストは変更者と同じ思い込みを共有していることが多い。

### 3. 観察する

- 期待した出力・ログ・状態変化が**実際に出ていること**を目視確認する。「エラーが出なかった」は成功の証拠として弱い。期待値が出たことを確認する。
- 正常系1本 + 変更に関係する境界1本(空入力・失敗パスなど)を最低ラインとする。

### 4. 変更前後の差を確認する(バグ修正の場合)

修正前は症状が再現し、修正後は再現しないことを**両方**確認する。修正後だけ確認すると「もともと再現していなかった」ケースを見逃す。

### 5. 報告に検証内容を書く

```
確認済み: <実行したコマンド/操作> → <観察した結果>
未確認: <動かしていない経路・環境>
```

環境の制約で動かせなかった場合は、ごまかさず「静的確認のみ。実行確認は未実施」と書く。

## アンチパターン

- `npm test` が緑になった時点で「完了しました、動作します」と報告する
- 実行はしたがログを読まず、exit code 0 だけ見て成功と判断する
- 動かせない言い訳を探す(たいていの環境で、最小の実行手段は工夫すれば作れる)
- 検証で見つけた小さな異常を「今回のスコープ外」として黙殺する(報告には含める)
