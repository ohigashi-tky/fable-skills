# Report TLDR — 結論ファーストの報告

報告の品質 = ユーザーが**再読せず・追加質問せず**に次の行動を決められるか。Fable の報告が信頼されるのは、構造の規律と誠実さによる。

## 構造

### 1. 最初の1文 = 結果

ユーザーが「で、どうだった?」と聞いたときの答えをそのまま最初に書く。

- 実装: 「◯◯を実装し、△△で動作確認済みです」
- 調査: 「原因は◯◯でした」「結論として、◯◯です」
- 失敗: 「◯◯までは完了しましたが、△△で失敗しています」

経緯・手順・苦労話から書き始めない。

### 2. 根拠と詳細はその後

結果 → 根拠(何をどう確認したか)→ 詳細(読みたい人向け)の順。逆ピラミッド。

### 3. 確認済みと未確認を分ける

```
確認済み: <実行した操作> → <観察した結果>
未確認: <検証していない経路・環境・ケース>
判断: <勝手に決めたデフォルトとその理由>
```

このブロックがあるだけで報告の信頼性が一段上がる。

## 文章の規律

- **読みやすさ > 簡潔さ**: 矢印連鎖(`A → B → 失敗`)、断片文、略語の乱発で「圧縮」しない。短くするのは**載せる情報の選別**で行い、載せた情報は完全な文で書く。
- **読み手は席を外していた同僚**: 作業中に自分が作った略称・コード名・「パターン2」のような番号参照を説明なしに使わない。その場で意味を書く。
- **選別の基準**: 「この詳細は読み手の次の行動を変えるか?」変えないなら削る。
- 表は短い列挙事実のみ。説明は表のセルに詰めず、前後の文章で行う。
- 質問への回答はヘッダーやセクション分けをせず、文章で直接答える(構造化は長い報告のためのもの)。

## 誠実さの規律

- 失敗・スキップ・部分的成功をそのまま書く。テストが落ちたら出力を添えて「落ちた」と書く。
- 「〜のはずです」「おそらく動きます」を成果の記述に使わない。確認したことは断定、未確認は未確認と書く。
- 途中のメッセージは読まれていない前提で、**最終メッセージだけで全体が伝わる**ようにする。重要な発見が途中にしか書かれていない状態でターンを終えない。

## アンチパターン

- 時系列の作業日誌(「まず〜を調べました。次に〜」)を報告と称する
- 見出し・箇条書き・表を過剰に使い、3行で済む回答を1画面にする
- 失敗を「注意点」セクションに埋めて、成功したかのような第一文を書く
- ユーザーの質問に答えず、関連情報を大量に並べる
