# Quality Pass — 出荷前の品質パス

「動く」と「出荷できる」の間にあるパス。Fable の diff がレビューで指摘されにくいのは、報告前にレビュアーの仕事を自分で済ませているから。

## 手順

### 1. diff をハンクごとに読む

`git diff` を出し、**書いた本人ではなくレビュアーの目**で1ハンクずつ読む。各ハンクに対する問い:

- このハンクはタスクに必要か?(ついで変更・デバッグ残骸は削除)
- もっと短く・平易に書けないか?
- 既存のユーティリティ・パターンで置き換えられないか?(車輪の再発明チェック: 似た処理を Grep)

### 2. コメント規律

以下のコメントを全て削除する:

- 変更理由の説明(「〜のため修正」)— それは PR 説明に書く内容
- 次の行が何をするかの説明(コードを読めば分かる)
- 「以前は〜だった」という歴史の記述
- レビュアーへの弁明(「この実装で正しい」)

残してよいのは「コードでは表現できない制約」のみ(なぜこの順序でなければならないか、外部システムの都合、既知の落とし穴)。

### 3. 周囲との整合

- 命名・エラー処理・ログの流儀が同ファイル・同モジュールの既存コードと揃っているか。
- 自分の好みのスタイルをプロジェクトに持ち込んでいないか(プロジェクトの流儀 > 一般的ベストプラクティス)。

### 4. 機械チェック

- リンター・フォーマッター・型チェックをプロジェクトの標準コマンドで実行する(package.json / Makefile / CI 設定を見て特定)。
- 触ったファイルに対する既存テストを実行する。

### 5. 削り残しチェック

- デバッグ print / console.log / 一時ファイル / コメントアウトされた旧コード
- 使われなくなった import・変数・関数(自分の変更で不要になったもの)
- TODO を書いた場合、それが「今やるべきこと」なら今やる

## 適用の目安

- 1〜2行の修正: ステップ4のみ
- 通常の実装: 全ステップ
- 大きい変更: 全ステップ + 可能なら独立エージェントに「この diff の簡素化・重複・バグを探せ」とレビューさせる

## アンチパターン

- 動いた瞬間の高揚感のままコミットする(このパスの存在意義)
- 品質パスでリファクタが膨らみ、スコープ外の変更が diff に混ざる(気づいた改善点は報告に書き、diff には入れない)
- リンターの警告を「既存でも出てるから」と自分の新規分まで放置する
