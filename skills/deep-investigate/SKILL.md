# Deep Investigate — 調査・分析の徹底手法

調査品質の差は「賢い検索クエリ」ではなく、**角度の数と検証の深さ**から生まれる。1つの角度は必ず何かを見落とす。

## 手順

### 1. 問いを分解する

- 調査の問いを、独立に答えられるサブクエスチョンに分解する(通常3〜6個)。
- 各サブクエスチョンに「何が分かれば答えたことになるか」を1行で付ける。

### 2. 多モードスイープ

同じ対象を**互いに盲目な複数の角度**から調べる:

- **構造で**: ディレクトリ構成・依存関係・設定ファイル(コード調査)/ 公式ドキュメント・仕様(外部調査)
- **内容で**: キーワード・エラーメッセージ・識別子での全文検索
- **時系列で**: git 履歴・CHANGELOG・リリースノート・issue の経緯
- **エンティティで**: 関係する人・チーム・モジュール・外部サービスを列挙し、それぞれの視点から見る

サブエージェントが使えるなら角度ごとに並列に投げる。各エージェントは他の角度の結果を知らない状態で調べさせる(バイアス防止)。

### 3. 三角測量

- 重要な主張は**2つ以上の独立した情報源**で確認する。1ソースの主張は「未確認」ラベル付きで扱う。
- ソース間で矛盾が出たら、それは調査の失敗ではなく最重要の発見。矛盾の理由(バージョン差・条件差・どちらかの誤り)を特定する。

### 4. 事実・推論・推測を分離する

結論をまとめる際、全ての文を3分類して書き分ける:

- **事実**: 観察した・実行した・原文にあった(根拠: file:line / URL / コマンド出力)
- **推論**: 事実から論理的に導いた(導出過程を書く)
- **推測**: 経験則・一般論からの見立て(「推測だが」と明記)

この分離を怠ると、読み手は全部を事実として受け取る。

### 5. 完全性チェック(最後に必ず)

報告を書く前に「批評家」として自分に問う:

- 回っていない探索モードはないか
- 未検証のまま報告に載っている主張はないか
- サブクエスチョンで答えていないものはないか
- 「調べたが何も出なかった」ことを報告に書いたか(ゼロ件も情報)

見つかった穴は、次のラウンドの調査として実行する(「今後の課題」として書き逃げしない。ただしユーザーの依頼範囲を超えるものは範囲外と明記して良い)。

## アンチパターン

- 最初の検索で出た筋の良さそうな answer に飛びつき、以降の調査がその確認作業になる
- 網羅を打ち切ったことを書かない(上位10件だけ見たのに全体の結論の顔をする)
- 矛盾する情報を黙って片方だけ採用する
- 推測を断定調で書く
