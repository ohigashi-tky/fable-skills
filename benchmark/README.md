# ベンチマーク

Skills の効果を3条件で比較してスコア化します。

- **A**: Opus + fable-skills
- **B**: Opus 素
- **C**: Fable 素

「A − B」が Skills の効果、「C − A」が Skills で埋まらないモデル差です。

## 課題

正解を仕込んであるので、正解キーと突き合わせて客観採点できます。

| ID | 課題 | 採点方法 |
|---|---|---|
| T1 | バグ探し(5個埋め込み済み) | 発見数と誤検出数 |
| T2 | 落ちるテストの原因調査と修正 | 根本原因を直したか、症状を隠しただけか |
| T3 | 仕様からレートリミッター実装 | 隠し受入テスト7本の通過数 |
| T4 | コード調査(質問6問) | 正答数 |

## 1ランの手順

```bash
# 1. 実行環境を作る(条件Aのときだけ --with-skills を付ける)
./benchmark/tools/setup-run.sh T1 /tmp/bench/T1-A-1 --with-skills
```

2. `/model` でモデルを条件に合わせ、作成されたディレクトリで新しいセッションを開始する
3. `TASK.md` の本文をそのままコピペして依頼する。追加の指示やヒントは与えない
4. 完了したら最終報告を `REPORT.md` としてそのディレクトリに保存する
5. `benchmark/answer-keys/<課題ID>.md` の手順で採点する(T3 は受入テストを実行)
6. `scoring/results-template.csv` の形式で `results.csv` に1行追記する

採点軸は6つ: correctness(正解キー照合)、verification(実際に動かして確認したか)、report(レポート品質)、autonomy(介入なしで完遂したか)、scope(依頼どおりの成果物か)、効率(分数・介入回数)。詳細は `scoring/rubric.md`。

report 軸だけは採点者のバイアスを避けるため、モデル名などを伏せた REPORT.md を `scoring/judge-prompt.md` と一緒に別セッションの LLM に渡して採点させます。

## 可視化

`tools/dashboard.html` をブラウザで開いて `results.csv` を貼り付けると、条件別の総合スコア、Skills 効果(A−B)、軸別レーダー、課題別バーが表示されます。

## 結果を信頼するための注意

- **反復**: 出力は揺れる。1条件×1課題につき最低3ラン、代表値は中央値。1ランでも方向性は見えるが、僅差の結論は出さない
- **汚染防止**: answer-keys/ を実行セッションに見せない(setup-run.sh はコピーしない)。実行ディレクトリとセッションは使い回さない
- **公平性**: 条件Bにだけ「もっと検証して」のような追加指示をしない。ブラインド審査に条件・モデル名を伝えない
- **順序**: 条件の実行順をラン毎に入れ替える(運用者が課題に慣れるため)
