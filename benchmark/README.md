# fable-skills ベンチマーク

Skills の効果を **3条件の比較実験**でスコア化・可視化するための仕組みです。

- **条件A**: Opus + fable-skills 導入済み
- **条件B**: Opus 素(Skills なし)
- **条件C**: Fable 素(Skills なし)

期待される結果: C ≧ A > B。「A が B をどれだけ上回るか」が Skills の効果、「C と A の差」が埋まらないモデル差です。

## 仕組みの全体像

```
benchmark/
  tasks/         課題(4種類)。フィクスチャ + 全条件共通のプロンプト
  answer-keys/   正解キー・隠し受入テスト ※実行セッションには絶対に見せない
  scoring/       採点ルーブリック・ブラインド審査用プロンプト・結果CSVテンプレート
  tools/         実行環境セットアップスクリプト・可視化ダッシュボード
```

採点は3層で行い、主観が入る余地を最小化しています:

| 層 | 内容 | 採点方法 |
|---|---|---|
| ①客観スコア | 正解キーとの一致(バグ発見数、テスト通過数、事実の正答数) | 機械的(チェックリスト照合・テスト実行) |
| ②プロセススコア | 検証を実際に実行したか、根拠 file:line があるか等 | レポート・作業ログからチェックリスト判定 |
| ③レポート品質 | 結論ファースト、確認済み/未確認の区別、読みやすさ | **条件を伏せた** LLM 審査(ルーブリック採点) |

## 課題一覧

| ID | 種類 | 測る能力 | 対応する Skill |
|---|---|---|---|
| T1 | バグ網羅探索 | 5個の埋め込みバグを何個見つけ、誤検出が何件か | parallel-explore, adversarial-verify |
| T2 | 根本原因デバッグ | 落ちるテストの根本原因を特定し、症状でなく機構を直せるか | root-cause-debug, evidence-verify |
| T3 | 仕様からの実装 | 仕様の境界ケースまで実装できるか(隠し受入テストで判定) | scope-and-plan, evidence-verify, quality-pass |
| T4 | コード調査・分析 | 6個の事実質問に正答できるか、根拠を示せるか | deep-investigate, report-tldr |

## 実行手順(1ラン)

### 1. 実行環境を作る

```bash
cd fable-skills
./benchmark/tools/setup-run.sh T1 /tmp/bench/T1-run01
```

課題フィクスチャ**だけ**が新しい git リポジトリとしてコピーされます(answer-keys は含まれません)。
条件Aのランでは、続けて Skills を導入します:

```bash
./benchmark/tools/setup-run.sh T1 /tmp/bench/T1-run01 --with-skills
```

### 2. セッションを実行する

1. Claude Code のモデルを条件に合わせて切り替える(`/model`)
2. `/tmp/bench/T1-run01` で**新しいセッション**を開始する
3. `TASK.md`(フィクスチャに同梱)の本文を**そのままコピペ**して依頼する。追加の指示・ヒントは与えない
4. 途中で質問されたら「お任せします」以外は答えない(介入回数として記録する)
5. 完了したら、最終報告メッセージ全文を `REPORT.md` として実行ディレクトリに保存する

### 3. 採点する

```bash
# ①客観 + ②プロセス: 正解キーのチェックリストと突き合わせる
cat benchmark/answer-keys/T1.md   # 照合手順が書いてある(T2/T3は採点テストを実行)

# ③レポート品質: ブラインド審査
#   REPORT.md から条件が分かる記述(モデル名等)を伏せ、
#   scoring/judge-prompt.md と一緒に別セッションの LLM に渡す
```

3層の結果を `scoring/results-template.csv` の形式で `results.csv` に追記します。

### 4. 可視化する

`tools/dashboard.html` をブラウザで開き、`results.csv` の内容を貼り付けると、条件別レーダーチャート・課題別スコア比較・効率(時間/介入回数)が表示されます。

## 実験計画の注意(結果の信頼性のために)

- **反復数**: LLM の出力は揺れます。1条件×1課題につき**最低3ラン**(推奨5)。代表値は中央値を使う。1ランずつでも方向性は見えますが、僅差の結論は出さないこと。
- **ブラインド採点**: ③の審査 LLM には条件・モデル名を絶対に渡さない。REPORT.md 内の「Fable」「Opus」等の文字列を伏せ字にしてから渡す。審査には Fable / Opus 以外も含め手持ちで最も強いモデルを使い、**全レポートを同じ審査モデルで**採点する。
- **順序効果**: 同じ課題を同じ人が続けて操作すると運用が上達する。条件の実行順をラン毎に入れ替える(A→B→C, C→A→B, ...)。
- **汚染防止**: answer-keys/ を実行セッションに見せない(setup-run.sh がコピーしない設計)。実行ディレクトリを使い回さない。前ランの続きのセッションで走らせない。
- **公平性**: 条件Bで「もっと検証して」等の追加指示をしない。プロンプトは TASK.md の文言のみ。
- **記録**: 各ランの所要時間(分)・介入回数(質問に答えた回数)・完遂したか(途中放棄/未完了)も CSV に記録する。品質が同点でも効率と完遂率に差が出ることが多い。

## スコアの見方

- **Skills の効果** = 条件A − 条件B(同一モデルなので純粋に Skills の寄与)
- **残るモデル差** = 条件C − 条件A(Skills で埋まらなかった分)
- 軸別に見ること: 経験上、①客観(特に網羅性・検証)と③レポート品質は Skills で大きく動き、T2 の「一発の仮説の深さ」はモデル差が残りやすい。どの軸が動いたかが次の Skill 改善の入力になります。
