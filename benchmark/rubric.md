# 採点ルーブリック(100点満点)

各課題は **auto スコア 0〜100**(スクリプトが機械採点)で評価する。全体スコアは4課題の平均。
採点に正解を知る人間・LLM は不要。隠しテストの実行と正解キー照合だけで決まる。

## auto スコア(headline・完全自動)

| 課題 | 採点方法 | 満点条件 |
|---|---|---|
| T1 バグ探し | `findings.json` の行番号を正解の8バグ行(±2行)に照合。1バグ=12.5点、誤検出1件=−12.5点(下限0) | 8バグ全発見・誤検出0 |
| T2 根本原因 | 隠し回帰テスト8件を実行し通過率×100。境界(誤差で上限を超えるケース)を含むため、症状潰しの修正では落ちる | 根本(積算の単位)を直し8/8通過 |
| T3 実装 | 隠し受入テスト18件を実行し通過率×100。負の金額・端数分配順・型/通貨検証を含む | 18/18通過 |
| T4 調査 | `answers.json` を正解キーの許容回答に照合。1問=1.0(部分0.5)、×100/8 | 8問正答 |

これらは `benchmark/answer-keys/` の隠しテスト・正解キーと `tools/grade.sh` で採点する。実行役の run ディレクトリには正解キーが入らない(`setup-run.sh` がコピーしない)ため、**実行役は正解を見られない**。

## quality スコア(0〜20・任意・ブラインド)

auto では測れない「報告の質」を測りたい場合のみ、`scoring/judge-prompt.md` で条件を伏せた別 LLM に採点させる。headline には含めない(採点者バイアスを headline に持ち込まないため)。

観点: 結論ファースト / 確認済み・未確認の書き分け / 根拠(file:line)の提示 / 自己完結性 / 誠実さ。

## 効率(参考・スコア外)

`minutes`(所要分)、`interventions`(実行役への追加指示回数)、`completed`(完遂 true/false)を記録する。auto が同点でも効率で差が出ることがある。

## 記録

1ラン1行で `results.csv` に追記する。列は `results-template.csv` を参照。
`condition` は A(対象モデル+Skills)/ B(対象モデル素)/ C(基準モデル素)。
